## 1. §1 trace completeness — the six numbered constraint-map claims

1. **`CrossFeedPair` shared between `StereoDelay::Process` and `Reverb::Process`** — verified. `app/dsp/Delay.hpp:726` calls `CrossFeedPair(dL, dR, cross)`; `app/dsp/Reverb.hpp:705` calls `CrossFeedPair(valB, valA, 0.0f)`. Both include `StereoField.hpp` and cross-reference each other in header comments. TRUE.
2. **`cross_feed_pair_is_identity_at_zero_and_an_equal_blend_at_one_half` pins the helper's arithmetic including the 0.5 midpoint, and only calls `dsp::CrossFeedPair` directly** — verified at `app/FroggersDspParityTests.cpp:6958-6967`. It never touches `StereoDelay`, so it is untouched by any repair confined to the delay's own weight computation. TRUE.
3. **`stereo_delay_cross_feed_reproduces_its_captured_output_exactly` is a self-capture, not a parity pin** — verified at `app/FroggersDspParityTests.cpp:6969-6988`; its own comment states the literals "were captured by running this same fixture against `dsp::StereoDelay::Process` before that de-duplication." TRUE.
4. **No firmware parity; `git show f236915^:sim/StereoDelay.hpp` carries `const float cross = p.dwid * 0.5f;` verbatim; no `StereoDelay` under `src/`** — ran the exact command; output matches verbatim. `find`/`grep` under `src/` for `StereoDelay` are empty; `src/core/FroggersEngine.hpp`'s only "delay" hits are an unrelated pre-delay/comb utility (`PureDelay`, `Comb`), not a stereo feedback delay. TRUE.
5. **`dwid == 0` makes the cross-feed a no-op at any `widthBalance`** — verified two ways: (a) algebraically, `cross = p.dwid * 0.5f * widthBalance` (`Delay.hpp:721`) is zero whenever `dwid` is zero regardless of `widthBalance`; (b) `widthSpread` is likewise zero-multiplied by `dwid`, so `timeL == timeR`, and by induction from identical zeroed initial state and symmetric per-channel processing (`inSignal`, `fbEff`, `freezeEff` are scalars shared by both `WriteSample` calls at `Delay.hpp:808-809`), `lineL` and `lineR` stay bit-identical for all time at `dwid==0`, making `dL==dR` and `CrossFeedPair(x,x,w)=={x,x}` for any `w`. TRUE.
6. **"Other pins that touch `Process`'s output" are complete at six** — **NOT confirmed complete.** See defect below.

**Enumeration by operand across `app/*.cpp`** (case-insensitive): `StereoDelay` 91, `dsp::StereoDelay` 70, `DelayWetPair` 41, `dwid` 30, `widthBalance` 9, `SetWidthBalance` 5, `CrossFeedPair` 5. Of the 31 `stereo_delay_*` test cases plus the two cross-feed-named tests, I individually inspected every one that sets `dwid`/width to a nonzero value or calls `.Process(`. All literal (bit-exact) pins that exercise a nonzero cross-feed resolve to exactly the three items named in the proposal's item 6 (`stereo_delay_default_knob_values_reproduce_original_output_exactly`, `stereo_delay_width_balance_mapping_keeps_cross_in_0_1_and_spread_at_or_below_todays_max`, and — inside the named "Freeze family" — `stereo_delay_freeze_at_default_reproduces_pinned_original_output_through_real_process`, which drives `width=0.25` via `MapRowsToDelayParams` and pins literal output `-0.11269673f`/`-0.0563911721f`). The remaining diffusion/reverse-blend tests with nonzero `dwid` use inequality/differential assertions, not literal pins, so they are lower-risk but still worth naming — they were not separately named, but they are covered by no family prefix at all (they're `stereo_delay_diffusion_*` / `stereo_delay_reverse_blend_*`, not in the "Freeze family" bucket the constraint map names). This is a second, milder completeness gap alongside the one below.

**DEFECT (blocking for tasks 1.2/1.4, not for 1.1):** `app/FroggersAudioRoutingTests.cpp:2537`, `TEST_CASE(delay_stereo_width_produces_a_stereo_image)`, sets Delay Feedback=0.7 and Stereo width=1.0 through the **full production router** (`FroggersBankId::Delay, 4`) and asserts `ChannelDifference(...) > 1e-4`. This is a genuine seventh pin on `StereoDelay::Process`'s output through the real signal chain, in the exact defect zone the proposal itself measured (Feedback 0.7, width 1.0). It does not surface under an operand grep for `StereoDelay`/`dwid`/`widthBalance`/etc. because it addresses the parameter by bank/slot index rather than by the C++ symbol names — confirmed by grepping `FroggersBankId::Delay, 4)` across `app/*.cpp` (2 hits: this test, and `FroggersSurfaceTests.cpp:2850`, which deliberately sets width to 0.0 to avoid the cross-feed and is not at risk). This is exactly the "enumerate by operand, not by name" failure the brief warned about: the mechanical sweep the constraint map claims to be complete misses an integration-level test because it isn't spelled the same way. Risk of actual breakage under a correct repair is low (the assertion is a weak inertness bound, and a repair that lowers correlation will very likely still exceed `1e-4`), but the proposal's own rule is "a seventh pin discovered from a red build later is a preflight failure now" — so this is named now rather than left to be discovered later. **Disposition: name `delay_stereo_width_produces_a_stereo_image` in the constraint map (item 6) and in task 1.4's enumeration before task 1.2/1.4 are dispatched.**
